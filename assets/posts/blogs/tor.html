The Tor Network: Anonymous Browsing and Hidden Services

Abstract

This post explores the Tor network in depth, detailing how users can browse the internet anonymously and how hidden services are hosted and accessed within the Tor ecosystem. It aims to demystify the technical process behind achieving online anonymity using Tor.

Anonymous Browsing

This part of the blog, discusses how a client connection is anonymized using Tor protocol. We will see a brief history of TOR, circuit establishment in tor network and multi-layer encryption/decryption protocol that provides anonymity to its users.

Introduction

First and foremost I want you to understand that confidentiality is not anonymity.

Confidentiality = "No one can read what I’m saying except authorized ones." (Encrypting messages with shared secrets between sender and receiver i.e. HTTPS)

Anonymity = "No one knows it’s me saying it." (Tor traffic hopping through different relays in tor network)

Tor stands for “The Onion Routing”, it is a decentralized network designed to provide anonymous communication on the internet. Tor protects users' privacy by routing traffic through a layered network of volunteer-operated servers, making it extremely difficult to trace online activity back to the user.

To use Tor, one simply needs a browser that supports the protocol. The Tor Browser, developed by the non-profit Tor Project, is the most trusted tool for this purpose. It can be downloaded from the project's official site and is straightforward to use: launch the browser, connect to the network, and begin browsing.

In regions where Tor is censored, users can still access it by configuring bridges—obfuscated relays not listed publicly, making them harder to detect and block. The Tor Browser has built-in support for such configurations.

A Brief History of Tor

The concept of onion routing was first developed in the 1990s by researchers at the U.S. Naval Research Laboratory, including Paul Syverson, Michael G. Reed, and David Goldschlag [ref]. Their goal was to secure online communications for U.S. intelligence by hiding metadata. In 2002, Roger Dingledine and Nick Mathewson, with continued input from Syverson, released the first public implementation of this concept [ref]. The project was soon named Tor.

By 2004, Tor was released under a free license, opening the door for global collaboration. In 2006, the non-profit Tor Project, Inc. was established to further its development. Since then, Tor has become a vital tool for journalists, whistleblowers, activists, and privacy-conscious individuals. The introduction of the Tor Browser and onion services made the technology more accessible to the general public.

How Tor Ensures Anonymity

To understand Tor's anonymizing capabilities, it's crucial to recognize the roles of its components. A typical Tor setup involves following:

  • User: The person who wants to browse anonymously.
  • Client: The Tor software (typically the Tor Browser) running on the user’s device.
  • Server: The destination website or service the user wants to access.
  • Tor Node (Relay): A volunteer-operated server in the Tor network that forwards traffic.
  • Tor Directory: provides a list of active tor nodes (relays) in the Tor network, it is maintained by trusted directory authorities.
  • Circuit: A temporary, encrypted path consisting of three random relays (Guard, Middle, and Exit) in the tor network through which traffic is sent.
    • Guard Node: the first relay and knows the user's IP address but not the final destination.
    • Middle Node: provides an additional layer of separation.
    • Exit Node: connects to the destination server but doesn't know the origin of the request.

    This segmentation ensures that no single node can determine both the source and destination. Each connection between nodes (client ↔ guard, guard ↔ middle, middle ↔ exit) uses its own local Circuit ID. Each node keeps a local mapping table to know which incoming ID maps to which outgoing ID and to find the corresponding decryption keys, and next hop in the outgoing circuit:

    Incoming Circuit ID → Decryption Key, Next Hop, Outgoing Circuit ID

Circuit establishment

When the Tor Browser starts, it retrieves the list of available nodes from the directory servers. Most of the censor authorities block requests to these directory to censor the tor. These directories are trusted servers that maintain an updated list of all public relays. The browser then selects three random nodes (Guard, Middle and Exit) to build a circuit.

Once the client selects the three relays, it initiates a secure circuit by negotiating session keys with each node in a telescoping manner as shown in the above figure.

  1. The client starts a circuit to the Guard node, creates a Circuit ID CID₁, and performs a key exchange to establish K₁.
  2. The client then extends the circuit to the Middle relay:
    • Sends a request to the Guard, encrypted with K₁, asking to extend to Middle.
    • Guard node picks a local CID for the Middle connection, and connects.
    • Client negotiates a key K₂ with Middle, through Guard.
  3. The clients then repeats the same with middle relay to add the Exit node, establishing key K₃.

At the end, the client knows:

  • The full path, i.e. Guard Node, Middle Node and Exit Node.
  • Shared keys: K₁, K₂, K₃
  • Its own Circuit ID to the Guard (say CID₁)

But it does not know or care about the relays’ internal Circuit IDs (CID₂, CID₃, etc.).

Tor Message Encryption and Decryption

To send messages, the client applies multiple layers of encryption. Let’s say the client wants to send an HTTP request to example.com. Let’s denote the payload as:

M = "GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"

Step 1: Onion Encryption by the Client

Client prepares the message by applying layered encryption, starting from the last node (exit) back to the first (guard):

E₃ = Encrypt(K₃, M)
E₂ = Encrypt(K₂, E₃)
E₁ = Encrypt(K₁, E₂)

So the client sends the following tor cell to guard node:

Tor Cell:
    Circuit ID: CID₁
    Payload: E₁ = Enc_K₁(Enc_K₂(Enc_K₃(M)))

Step 2: Guard Node Decrypts 1st Layer

Guard Node receives the tor cell, then uses CID₁ to look up the key K₁ and decrypts the received payload:

Decrypt(K₁, E₁) → E₂
After removing the first layer of encryption, it forwards the following tor cell to middle node:
Tor Cell:
    Circuit ID: CID₂ (new, internal)
    Payload: E₂

Step 3: Middle Node Decrypts 2nd Layer

Middle Node receives the cell, then uses CID₂ to find K₂ and decrypts the received payload:

Decrypt(K₂, E₂) → E₃
After removing the second layer of encryption, it forwards the following tor cell to exit node:
Tor Cell:
    Circuit ID: CID₃
    Payload: E₃

Step 4: Exit Node Decrypts 3rd Layer

Exit Node receives the cell, then uses CID₃ to get K₃ and decrypts the received payload:

Decrypt(K₃, E₃) → M
After removing the last layer of encryption, exit node able to get the original request to be sent to the server.
M = "GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"

Finally, the Exit node sends this request to example.com over the public internet. The reply from example.com is then forward back to the client in a similar fashion by applying each layer of encryption one by one.

In this way tor provides anonymity to its users. Here’s the summary of what each node knows:

Node Knows Your IP? Knows Destination? Knows Message Content?
Guard ✅ Yes ❌ No ❌ No
Middle ❌ No ❌ No ❌ No
Exit ❌ No ✅ Yes ✅ Yes (if not using HTTPS)

All Tor traffic over the network is broken into 512-byte cells. This size is strictly enforced, making Tor traffic highly uniform and hard to fingerprint.

Tips for Safer Browsing with Tor

  • Don’t resize your browser window — it can be used to fingerprint your device.
  • Don’t install extra browser plugins or scripts.
  • Use HTTPS websites whenever possible (Tor Browser has HTTPS-Only Mode).
  • Avoid logging into personal accounts unless absolutely necessary

TOR Hidden Services

This part of the blog, discusses about the TOR hidden services and step-by-step process of setting up the hidden service on the TOR network.

What Is a Hidden Service?

A Tor Hidden Service (also known as an Onion Service) is a server that can be accessed only through the Tor network. Unlike traditional websites, a Hidden Service hides its real IP address from clients, and clients also hide their IP addresses from the service. This mutual anonymity ensures that neither party knows the physical location of the other, providing strong privacy protections.

Examples of Hidden Services are URLs ending with .onion (e.g., xyzabc1234[...]7890abcd.onion).

Components Involved

To understand working mechanism of hidden services it is crucial to understand the following terminology:

  • Client: The user who wants to visit a .onion site through Tor.
  • Hidden Service (HS): The server hosting the .onion site.
  • Introduction Points (IPs): Regular Tor relays selected by the Hidden Service to receive connection requests from clients.
  • Hidden Service Directory (HSDir): A distributed hash table (DHT) across Tor relays that stores Hidden Service descriptors.
  • Rendezvous Point (RP): A Tor relay chosen by the client where the client and Hidden Service will meet and establish communication.

Step-by-Step Flow

As shown above, both the client and the hidden service build circuits through Tor relays, using Introduction Points and Rendezvous Points to meet without revealing their IP addresses.

Now let's explore working mechanism of the hidden service step by step from service setup phase to establishing end-to-end encrypted communication with clients:

  1. Hidden Service Setup

    When the hidden service starts:

    • It randomly selects a few Tor relays as its Introduction Points (IPs) (typically 3).
    • It establishes Tor circuits (encrypted paths) to these IPs.
    • It creates a Hidden Service Descriptor, containing:
      • The service’s public key.
      • A list of its Introduction Points (with encrypted authentication tokens).
      • A digital signature for verification.
    • The descriptor is then uploaded to multiple Hidden Service Directories (HSDirs), distributed across the Tor network.
    • The descriptor is indexed using a hash derived from the .onion address and the current date to ensure freshness.

  2. Client Initiates a Connection

    When a client wishes to connect to a Hidden Service:

    • The client knows only the .onion address (e.g., xyzabc1234567890.onion).
    • In Tor v3 addresses, this address is derived from the service’s public key using base32 encoding.

  3. Client Fetches the Hidden Service Descriptor

    The client:

    • Computes the descriptor ID using the service’s public key and the current time period.
    • Downloads the descriptor from the appropriate Hidden Service Directories (HSDirs).
    • From the descriptor, the client learns:
      • The public key of the Hidden Service.
      • The list of Introduction Points it can use to contact the service.

  4. Client Sets Up a Rendezvous Point

    • The client selects a random Tor node to act as the Rendezvous Point (RP).
    • It builds a Tor circuit to the RP and sends it a rendezvous cookie (a random secret used to match connections).
    • The client keeps this circuit open, waiting for the Hidden Service to join.

  5. Client Contacts an Introduction Point

    The client:

    • Builds a Tor circuit to one of the Hidden Service’s Introduction Points.
    • Sends an encrypted message (using the Hidden Service’s public key) containing:
      • The address of the chosen Rendezvous Point.
      • The rendezvous cookie.
      • Its own temporary public key for secure session setup.
    • The Introduction Point forwards this encrypted message to the Hidden Service.

  6. Hidden Service Connects to the Rendezvous Point

    Upon receiving the client’s request:

    • The Hidden Service builds a Tor circuit to the specified Rendezvous Point.
    • It sends the same rendezvous cookie to the RP to identify the session.

    At this stage, both the client and the Hidden Service have circuits established to the same RP.

  7. Communication Begins

    • The Rendezvous Point links the two circuits together using the shared rendezvous cookie.
    • From now on, the client and the Hidden Service exchange data through the RP.

End-to-end encryption ensures that even the RP cannot read the traffic or know who either party is. The communication remains completely anonymous for both sides. To set up your own hidden service follow this.

Onion Address Length

The length of a .onion address depends on the version of the Tor Hidden Service protocol. Tor v3 is the current version and recommends:

  • 56 characters (excluding .onion suffix)
  • Example:
    m5kijz63lvevrfjcf7gfwzv2e5mmpk3so3nsxukgrvubqn7i6j5s7iid.onion
  • It is derived from following structure:
    • 256-bit Ed25519 public key
    • A checksum
    • A version number
  • Then base32-encoded to form the 56-character address:
    [base32(pubkey | checksum | version)].onion
  • Provides significantly improved cryptographic security compared to earlier versions.
